# HTTP-сервер claude-wt вешает демона

Найдено 2026-08-06 ночью, при попытке включить `claudeWtHttpPort` на popstas-pc.
Правка откатана, порт закрыт, живой конфиг восстановлен из `.bak`. Код в
репозитории остался — включать снова только после того, как это разобрано.

## Симптом

Через 2–3 минуты после старта приложения событийный цикл node встаёт намертво:

- строки `monitor: rss …` (раз в минуту) обрываются и больше не идут;
- HTTP перестаёт отвечать совсем — запросы не доезжают даже до строки
  `HTTP POST …` в логе, хотя порт остаётся в `LISTENING`;
- процесс жив, TCP-соединение висит в `ESTABLISHED`.

Лечится только перезапуском приложения. И снова встаёт через те же 2–3 минуты.

## Доказательство, что дело в сервере

Отметки `monitor: rss` из `%APPDATA%\windows-mqtt\windows-mqtt.log` — они идут
строго раз в минуту, пока цикл жив, и потому годятся как пульс.

| Состояние | Что в логе |
|---|---|
| Старая сборка, сервера нет | `03:18 … 04:03` — **46 минут без единого пропуска** |
| `claudeWtHttpPort: 9722`, запуск 04:04:11 | тики 04:04, 04:05, 04:06 → **обрыв**, дальше тишина до перезапуска |
| `claudeWtHttpPort: 9722`, запуск 04:10:24 | тики 04:10, 04:11, 04:12, 04:13 → **обрыв**, дальше тишина |
| Откат, сервера нет, запуск 04:20 | `04:20 … 04:25+` — тики идут |

Сорок шесть минут до, два обрыва подряд с сервером, чисто после отката. Совпадением
это быть уже не может.

## Что было включено

- `claudeWtHttpPort: 9722` рядом с `claudeWt: true` в блоке `windows` —
  `src/modules/windows.js` поднимает `winMan.startHttpServer(port)` в том же
  процессе, где тикает демон.
- Маршруты: `POST /claude-wt/status` (слоты) и `POST /claude-wt/focus` (подъём
  окна по id) — их спрашивает пикер ccfzf-picker.

Оба маршрута успели отработать правильно до зависания: статус отдал слоты с
pid демона, focus корректно отказал незнакомой сессии с причиной. То есть
логика верна, ломается что-то под ней.

## Ведущая догадка

**`claudeWtStatus()` из обработчика запроса.** Оба маршрута зовут её первой, и
оба зависания начинались сразу после запроса, который её вызвал. Внутри:

```js
const state = liveState ?? readState(cfg.statePath);
```

`cfg.statePath` лежит на `V:` — сетевом диске. Про чтение с него в этом проекте
уже собран целый список граблей (кэш SMB, врущий `mtime`, открытие файла с
правом записи перед чтением). Синхронное чтение оттуда в обработчике блокирует
единственный поток node, и если SMB не отвечает — оно не блокирует его на
секунду, а вешает насовсем.

Косвенное подтверждение: `claudeWtStatus()` зовёт и сторож демона, но раз в
30 секунд и всегда с прогретым `liveState`. Новые обработчики — первые, кто
дёргает её по чужому запросу, в произвольный момент.

Догадка не проверена. Прямо она не объясняет, почему цикл встаёт **без**
входящих запросов (второе зависание случилось через три минуты после
единственного запроса на 04:10:24) — возможно, встал он именно тогда, а
следующие два тика успели пройти по уже запущенному таймеру.

## Что проверить дальше

1. Снять стек зависшего процесса: `node --inspect` либо
   `Get-CimInstance Win32_Process` + дамп, и увидеть, стоит ли он на чтении `V:`.
2. Прогнать сервер с маршрутом, который **не** зовёт `claudeWtStatus()` (отдаёт
   константу). Если демон живёт — виновата она, а не сам `http.createServer`.
3. Если подтвердится: отдавать слоты только из `liveState`, а при его отсутствии
   отвечать `{ok: false, reason: 'daemon has no state yet'}` вместо чтения с
   диска. Пикер такой отказ уже гасит молча.
4. Заодно посмотреть на `focusSession`: `findOpenTerminalByTitle` зовёт
   `getWindows()` (~31 мс CPU), а `focusTerminalWindow` — `VirtualDesktop11.exe`.
   Обе вещи в обработчике тоже стоят на общем потоке.

## Как собирать этот репозиторий

Не через ssh. `npm run deploy-local` падает сразу:

```
Error: UNKNOWN: unknown error, stat 'D:\projects\js\windows-mqtt\node_modules\windows11-manager'
    at Object.realpathSync (node:fs:2800:17)
    at prepareDeps (scripts/deps-bundle.js:68:17)
```

`node_modules\windows11-manager` — юнкция. Из ssh-сессии (она в session 0 как
служба) `realpathSync` на ней отдаёт `UNKNOWN` (errno -4094); в интерактивной
сессии та же операция резолвится. Собирать только через планировщик:

```
schtasks /create /tn wm-deploy /tr "<путь к .cmd>" /sc once /st 00:00 /ru <user> /it /f
schtasks /run /tn wm-deploy
```

Тот же приём, каким `deploy-win.sh` в ccfzf-picker поднимает пикер в
интерактивной сессии.

`npm run deploy-fast` при этом отказывается своим ходом, пока в репозитории
есть невыкаченные правки `src-tauri`, `frontend-src`, `sessions.html`: интерфейс
пикера вшит в бинарник, быстрым путём он не доедет.
