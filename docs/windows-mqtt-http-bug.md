# Почему http-сервера claude-wt здесь больше нет

2026-08-06. Сервер библиотеки, поднятый внутри процесса демона, вешал его
событийный цикл. Разбирать причину не стали: обмен переехал на файл, и сервер
оказался не нужен вовсе. Этот документ остаётся затем, чтобы его не завели
заново.

## Что было

Ключ `claudeWtHttpPort` рядом с `claudeWt: true` поднимал
`winMan.startHttpServer(port)` в том же процессе, где тикает демон. Два маршрута:
`POST /claude-wt/status` (у кого из сессий открыто окно) и `POST /claude-wt/focus`
(подъём окна по id). Спрашивал их пикер ccfzf-picker, раз в секунду.

Внутри процесса демона — намеренно: `claudeWtStatus()` отдаёт `liveState` из
памяти, а в чужом процессе тот же вызов читал бы состояние с диска, то есть
расклад на момент последней записи.

## Симптом

Через 2–3 минуты после старта приложения событийный цикл node вставал намертво:

- строки `monitor: rss …` (раз в минуту) обрывались и больше не шли;
- HTTP переставал отвечать совсем — запросы не доезжали даже до строки
  `HTTP POST …` в логе, хотя порт оставался в `LISTENING`;
- процесс жив, TCP-соединение висит в `ESTABLISHED`.

Лечилось только перезапуском. И вставало снова через те же 2–3 минуты.

## Доказательство, что дело в сервере

Отметки `monitor: rss` из `%APPDATA%\windows-mqtt\windows-mqtt.log` идут строго
раз в минуту, пока цикл жив, и потому годятся как пульс.

| Состояние | Что в логе |
|---|---|
| Старая сборка, сервера нет | `03:18 … 04:03` — **46 минут без единого пропуска** |
| `claudeWtHttpPort: 9722`, запуск 04:04:11 | тики 04:04, 04:05, 04:06 → **обрыв**, дальше тишина до перезапуска |
| `claudeWtHttpPort: 9722`, запуск 04:10:24 | тики 04:10, 04:11, 04:12, 04:13 → **обрыв**, дальше тишина |
| Откат, сервера нет, запуск 04:20 | `04:20 … 04:25+` — тики идут |

Сорок шесть минут до, два обрыва подряд с сервером, чисто после отката.
Совпадением это быть уже не может.

Логика при этом была верна: статус успел отдать слоты с pid демона, focus
успел корректно отказать незнакомой сессии с причиной. Ломалось что-то под ней.

## Ведущая догадка, оставшаяся непроверенной

`claudeWtStatus()` из обработчика запроса. Оба маршрута зовут её первой, и оба
зависания начинались сразу после запроса, который её вызвал. Внутри:

```js
const state = liveState ?? readState(cfg.statePath);
```

`cfg.statePath` лежит на `V:` — сетевом диске. Про чтение с него в этом проекте
уже собран целый список граблей (кэш SMB, врущий `mtime`, открытие файла с
правом записи перед чтением). Синхронное чтение оттуда в обработчике блокирует
единственный поток node, и если SMB не отвечает — оно не блокирует его на
секунду, а вешает насовсем.

Прямо эта догадка не объясняет, почему цикл встал **без** входящих запросов:
второе зависание случилось через три минуты после единственного запроса. Возможно,
встал он именно тогда, а следующие два тика прошли по уже запущенному таймеру.

Догадку не проверяли и проверять не планируем — см. ниже.

## Чем заменили

Файлом, и это оказалось лучше по существу, а не только безопаснее.

- **Данные.** Демон пишет `claudeWt.windowsFile` (`src/claude-wt/windows-file.js`
  в windows11-manager): у какой сессии открыто окно, на каком столе, плюс `host`
  и `pid` демона. Файл ложится на ту же шару, и его читает `ccfzf --state` на
  стороне агента — локально, у себя. Направление важно: все известные грабли SMB
  относятся к чтению *с* шары, а тут с шары читает только Windows, и то, что
  писал сам.
- **Просьба о подъёме окна.** MQTT, топик `<base>/windows/claude-focus` — тот же,
  которым пользуется панель openHASP. Приёмник уже был.
- **Право на передний план.** Раньше pid демона приезжал в ответе
  `/claude-wt/status`; теперь он лежит в том же файле и доезжает до пикера полем
  `windowPid` в ответе агрегатора.

Побочно исчез целый класс состояний: пометка об окне больше не может пережить
погасший трекер. Свежесть проверяет тот, кто файл читает, — старше двух минут
он считается брошенным.

## Если сервер всё-таки понадобится

CLI-сервер библиотеки (`node src/index.js --port …` с `/place`, `/store`,
`/restore`, `/desktop`, `/claude-wt/restore`) существовал до всей этой истории и
живёт как жил: он в своём процессе и демону ничем не мешает. Ломалось именно
совмещение в одном процессе.

`startHttpServer` намеренно **не** экспортируется из `src/lib/index.js` — ровно
затем, чтобы поднять его внутри демона было нельзя по недосмотру. Прежде чем
возвращать, проверьте догадку выше: снимите стек зависшего процесса и посмотрите,
стоит ли он на чтении `V:`.

## Как собирать этот репозиторий

Не через ssh напрямую. `npm run deploy-local` падает сразу:

```
Error: UNKNOWN: unknown error, stat 'D:\projects\js\windows-mqtt\node_modules\windows11-manager'
    at Object.realpathSync (node:fs:2800:17)
    at prepareDeps (scripts/deps-bundle.js:68:17)
```

`node_modules\windows11-manager` — юнкция. Из ssh-сессии (она в session 0 как
служба) `realpathSync` на ней отдаёт `UNKNOWN` (errno -4094); в интерактивной
сессии та же операция резолвится. Плюс установленное приложение живёт значком в
трее и, запущенное из session 0, окажется там, где нет ни трея, ни рабочего
стола.

Поэтому сборка уезжает в задачу планировщика:

```
schtasks /create /tn wm-deploy /tr "<путь к .cmd>" /sc once /st 00:00 /ru <user> /it /f
schtasks /run /tn wm-deploy
```

Готовый скрипт с этой обвязкой (git pull в обоих репозиториях, задача, ожидание
и хвост лога) лежит рядом с выкаткой пикера, вне git: он знает имена машин и пути
конкретной установки, а не проекта.

`npm run deploy-fast` при этом отказывается своим ходом, пока в репозитории есть
невыкаченные правки `src-tauri`, `frontend-src`, `sessions.html`: интерфейс
пикера вшит в бинарник, быстрым путём он не доедет. После `git pull` эти файлы
всегда свежее установленного exe, поэтому первый прогон после подтягивания
коммитов обязан быть полным.
